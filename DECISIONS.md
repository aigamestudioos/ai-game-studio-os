## Incremento 0.1 — Monorepo Bootstrap

### [2026-07-15] pnpm 10.32.1 fixado no `packageManager`
**Contexto:** ADR-002 exige `packageManager` fixado no `package.json` raiz, mas não define a versão (SPECs só fixam o piso `pnpm ≥9`).
**Decisão:** `"packageManager": "pnpm@10.32.1"`.
**Motivo:** Versão já disponível e verificada no ambiente de desenvolvimento (Codespace).
**Impacto:** Builds reproduzíveis com essa versão exata; atualizar aqui se o ambiente mudar de versão.

### [2026-07-15] TypeScript strict, `target: ES2022`, `moduleResolution: Bundler`
**Contexto:** SPEC-001 exige apenas "TypeScript em modo estrito", sem enumerar flags específicas.
**Decisão:** `tsconfig.base.json` com `strict: true`, `noUncheckedIndexedAccess: true`, `moduleResolution: "Bundler"`, `verbatimModuleSyntax: true`, `module: "ESNext"`.
**Motivo:** Configuração padrão atual para monorepos que consumirão Next.js (Incremento 0.2) via bundler, sem exigir extensões explícitas em imports relativos.
**Impacto:** Todos os packages herdam via `extends`. Qualquer package com necessidade diferente deve justificar o desvio aqui.

### [2026-07-15] ESLint 9 flat config, sem Husky/lint-staged nesta etapa
**Contexto:** SPEC-001 lista ESLint, Prettier, Husky e lint-staged como ferramentas de qualidade, mas o escopo explícito do Incremento 0.1 pediu apenas `eslint.config.mjs` e `prettier.config.mjs`.
**Decisão:** `eslint.config.mjs` (flat config) com `@eslint/js` + `typescript-eslint` recommended + `eslint-config-prettier`. Husky/lint-staged adiados.
**Motivo:** Respeitar o escopo explícito do incremento ("apenas estrutura"); hooks de commit fazem mais sentido quando já houver código de aplicação sendo commitado com frequência.
**Impacto:** Nenhuma validação automática de lint no pre-commit ainda — lint roda apenas via `pnpm lint` manual/CI (CI ainda não existe, é o Incremento 0.4).

## Incremento 0.2 — Next.js + App Router

### [2026-07-15] `apps/web` criado manualmente, sem `create-next-app`
**Contexto:** `create-next-app` gera Tailwind, ESLint config e estrutura próprios que conflitam com as convenções do monorepo (ADR-002, ARCHITECTURE.md §3) e com o escopo do incremento, que exclui Tailwind/shadcn/Supabase.
**Decisão:** Scaffold manual de `apps/web` (package.json, tsconfig.json estendendo `tsconfig.base.json`, next.config.mjs, `app/layout.tsx|page.tsx|loading.tsx|error.tsx|not-found.tsx`), usando Next 15.5.20 + React 19.2.7 (últimas versões estáveis das linhas 15/19 no momento do incremento).
**Motivo:** Controle total sobre estrutura e convenções desde o início; evita remover/desfazer artefatos gerados que não seriam usados.
**Impacto:** Nenhum arquivo de configuração duplicado ou conflitante; `apps/web` segue o mesmo padrão de `packages/*` (tsconfig via `extends`, scripts padronizados).

### [2026-07-15] `verbatimModuleSyntax: false` em `apps/web/tsconfig.json`
**Contexto:** `tsconfig.base.json` define `verbatimModuleSyntax: true` (Incremento 0.1), mas os arquivos de tipos gerados pelo Next (`next-env.d.ts`, `.next/types/**`) e a convenção de `next.config.mjs` não seguem essa exigência de `import type` explícito.
**Decisão:** Sobrescrever para `false` apenas em `apps/web/tsconfig.json`.
**Motivo:** Evitar atrito com arquivos gerados pelo próprio Next.js, que a ferramenta regenera automaticamente e não podemos ajustar.
**Impacto:** Restrito a `apps/web`; todos os `packages/*` continuam com `verbatimModuleSyntax: true`.

### [2026-07-15] `turbo.json`: `outputs` do task `build` inclui `.next/**`
**Contexto:** O pipeline `build` original só declarava `dist/**` como output (válido para os packages), mas o build do Next gera `.next/**`, causando warning "no output files found" no cache do Turborepo.
**Decisão:** `"outputs": ["dist/**", ".next/**", "!.next/cache/**"]`.
**Motivo:** Cache correto do Turborepo para `apps/web`, excluindo o diretório de cache interno do Next (não determinístico, não deve ser cacheado pelo Turborepo).
**Impacto:** Nenhum impacto nos packages existentes (continuam gerando apenas `dist/**`).

## Incremento 0.3 — Tailwind v4 + Design Tokens + Dark Mode + ThemeProvider

### [2026-07-15] Tokens e ThemeProvider ficam em `apps/web`, não em `packages/ui`
**Contexto:** SPEC-005 §5 define tokens/providers dentro de `packages/ui/{tokens,providers}`, mas isso faz parte da estrutura completa do design system (`server/client/shared/base/composed/...`), cuja implementação a própria SPEC-005 §14 agenda para o "Sprint 2", não para este incremento.
**Decisão:** Tokens Tailwind em `apps/web/app/globals.css`; `ThemeProvider`/`useTheme` em `apps/web/providers/` e `apps/web/hooks/` (pastas já scaffolded no Incremento 0.2). `packages/ui` permanece stub.
**Motivo:** Escolha explícita do usuário para não antecipar a estrutura completa de `packages/ui` antes da hora, mantendo o incremento pequeno e focado.
**Impacto:** Quando `packages/ui` for construído no Sprint 2, o `ThemeProvider` e os tokens precisarão ser migrados/generalizados para lá (hoje acoplados a `apps/web`). Nenhum outro app consome esses tokens ainda, então não há duplicação por enquanto.

### [2026-07-15] Sem persistência de tema neste incremento
**Contexto:** ARCHITECTURE.md proíbe `localStorage`/`sessionStorage`. Persistência real de preferência de usuário dependeria de Supabase Auth, que só chega no Incremento 0.7.
**Decisão:** `ThemeProvider` mantém o tema apenas em memória (React state) nesta etapa; dark-first por padrão; detecção de `prefers-color-scheme` via script inline no `<head>` do `layout.tsx` (executa antes do primeiro paint, sem usar storage) evita flash na carga inicial, mas a escolha explícita do usuário não sobrevive a um reload.
**Motivo:** Escolha explícita do usuário — persistência real fica para quando houver Auth/preferência de usuário no banco.
**Impacto:** Toggle de tema funciona durante a sessão (validado manualmente via `next dev`), mas reseta para o padrão do sistema a cada reload até o Incremento 0.7.

## Incremento 0.4a — Fundação do Design System + shell do `/playground`

### [2026-07-15] Sprint 0.4 dividido em 0.4a/0.4b/0.4c
**Contexto:** A instrução original de "Sprint 0.4" pedia 21 componentes com matriz completa de estados (default/hover/focus/pressed/disabled/loading/success/warning/error), dark/light, acessibilidade, e um playground de 16 seções interativas — muito acima do limite de ~10 arquivos novos / 50 alterados por incremento (`CLAUDE.md`).
**Decisão:** Dividir em três subincrementos: 0.4a (fundação: Button, Input, Textarea, Card, Badge, Avatar + shell do playground), 0.4b (componentes avançados: overlays/feedback), 0.4c (playground completo + demais componentes e seções). Formalizado em `ADR-005-sprint-governance.md`.
**Motivo:** Escolha explícita do usuário, aprovando a proposta de divisão apresentada.
**Impacto:** Cada subincremento tem seu próprio ciclo de validação/documentação/commit, mantendo os limites de tamanho de sprint.

### [2026-07-15] Tokens `success`/`warning` adicionados a `globals.css`
**Contexto:** SPEC-005 §4 lista tokens de superfície e semânticos obrigatórios, mas não inclui `success`/`warning` — e este sprint exige que todo componente suporte esses estados sem cor hardcoded.
**Decisão:** Adicionar `--success`/`--success-foreground`/`--warning`/`--warning-foreground` (valores oklch, dark-first + override em `[data-theme="light"]`) e os respectivos `--color-success*`/`--color-warning*` no bloco `@theme`.
**Motivo:** SPEC-005 define tokens "obrigatórios", não uma lista fechada — extensão necessária para cumprir um requisito explícito deste sprint sem violar a regra de "nunca cor hardcoded".
**Impacto:** Nenhum impacto em tokens existentes; `Button` e `Badge` já usam `success`/`warning` como variantes.

### [2026-07-15] Reversão da persistência de tema via cookie
**Contexto:** No planejamento deste sprint, cookie-based persistence havia sido a opção recomendada e aprovada para resolver o conflito entre "validar persistência" e a proibição de `localStorage`/`sessionStorage`. Antes da implementação ser finalizada, o usuário reverteu essa escolha.
**Decisão:** Manter o `ThemeProvider` apenas em memória (React state) nesta etapa, sem gravar cookie. Nenhuma mudança de código chegou a ser commitada com a abordagem de cookie.
**Motivo:** Evitar uma solução de persistência intermediária/temporária; persistência real será implementada junto com Supabase Auth (Incremento 0.7), reduzindo complexidade arquitetural (uma única fonte de verdade — preferência do usuário no banco — em vez de cookie + banco depois).
**Impacto:** Nenhum. A decisão do Incremento 0.3 ("sem persistência até 0.7") permanece válida e não precisou ser revertida — a tentativa de mudança neste sprint não chegou a ser commitada.

### [2026-07-15] Bug de layout: `max-w-{sm,md,lg,xl}` colide com os tokens de espaçamento
**Contexto:** Validação visual com Playwright (screenshots de `/playground`) revelou que `Input`, `Textarea` e `Card` renderizavam muito mais estreitos que o esperado. Nem `pnpm build`, `pnpm lint` nem `pnpm typecheck` detectaram o problema — só a inspeção visual. Causa raiz: o Tailwind v4 usa uma escala de `spacing` compartilhada para resolver utilities nomeadas de tamanho (`max-w-*`, `w-*`, `h-*`, etc.) quando não há uma escala dedicada com o mesmo nome. Como definimos `--spacing-sm/md/lg` em `globals.css` (Incremento 0.3, para `p-*`/`gap-*`), o Tailwind passou a resolver `max-w-md` como `var(--spacing-md)` (1rem) em vez do valor padrão (~28rem) — confirmado no CSS compilado: `.max-w-md { max-width: var(--spacing-md); }`.
**Decisão:** Substituir `max-w-md` por `max-w-[28rem]` (valor arbitrário) nos dois containers afetados em `apps/web/app/playground/page.tsx`. Não renomear os tokens de espaçamento (usados corretamente em `p-*`/`gap-*`/`px-*`/`py-*` em todos os componentes).
**Motivo:** Correção cirúrgica no ponto de uso, sem alterar os tokens do design system (que continuam corretos para seu propósito original — padding/gap).
**Impacto:** **Risco sistêmico a observar nos próximos incrementos (0.4b/0.4c):** qualquer uso de `w-sm`, `w-md`, `w-lg`, `h-sm`, `h-md`, `h-lg`, `min-w-*`/`min-h-*` com esses mesmos nomes (`sm`/`md`/`lg`) vai colidir do mesmo jeito. Ao dimensionar containers/larguras fixas, preferir a escala numérica padrão do Tailwind (`max-w-96`, `w-64`, etc.) ou valores arbitrários (`max-w-[28rem]`), nunca os nomes `sm`/`md`/`lg`/`xl` para as famílias `w-*`/`h-*`/`max-w-*`/`min-w-*`/`min-h-*`.

## Incremento 0.4b — Componentes avançados

### [2026-07-15] Dialog + Modal combinados em um arquivo; Toast + Toaster combinados em outro
**Contexto:** O escopo aprovado do 0.4b tem 10 componentes (Dialog, Modal, Toast, Tooltip, DropdownMenu, Alert, Spinner, Skeleton, Separator, Progress). Um arquivo por componente no padrão shadcn geraria 12 arquivos (Toast sozinho precisaria de toast.tsx + toaster.tsx + hook), passando do limite de 10 arquivos novos por incremento (`CLAUDE.md`).
**Decisão:** `dialog.tsx` exporta tanto a família `Dialog*` (Radix Dialog, dispensável) quanto `Modal*` (Radix AlertDialog, não dispensável — exige ação explícita); `toast.tsx` exporta os primitivos de Toast e o componente `Toaster` (renderer); `hooks/use-toast.ts` fica separado por já existir a convenção de hooks em `apps/web/hooks/`.
**Motivo:** Manter os 10 componentes pedidos sem exceder o limite de arquivos novos — Dialog/Modal são a mesma família semântica (overlay modal), assim como Toast/Toaster (primitivo + renderer do mesmo conceito).
**Impacto:** Nenhum a nível de API pública — cada componente é importado normalmente pelo nome (`Dialog`, `Modal`, `Toast...`, `Toaster`). Se o arquivo crescer demais no futuro, pode ser desmembrado sem quebrar consumidores (basta manter os mesmos exports, movidos para arquivos separados).

### [2026-07-15] Toast usa estado global via módulo (não Context React)
**Contexto:** `toast({ title, description })` precisa poder ser chamado de qualquer componente/Server Action/handler, não só de dentro de uma árvore React específica.
**Decisão:** `hooks/use-toast.ts` mantém um array de toasts em uma variável de módulo, com um `Set` de listeners; `toast()` e `dismissToast()` mutam esse estado e notificam os listeners; `useToast()` é o hook que assina esse estado para re-renderizar. O `Toaster` (dentro de `ToastProvider` do Radix, que só cuida de posicionamento/acessibilidade) é o único consumidor de `useToast()` que efetivamente renderiza os toasts.
**Motivo:** Padrão simples e testado (mesma técnica usada pelo shadcn/ui), sem dependência externa nova, e sem exigir um Provider próprio além do já necessário do Radix.
**Impacto:** Estado de toasts é global à aba do navegador (não por Server Component/request) — comportamento esperado para notificações client-side.

### [2026-07-15] Token `--backdrop` criado para overlays de Dialog/Modal
**Contexto:** Overlay inicialmente usava `bg-surface-inverse/60`, mas `surface-inverse` inverte de valor entre os temas (claro no dark mode, escuro no light mode) — resultado: o overlay ficava claro/lavado no dark mode em vez de escurecer o conteúdo por trás. Encontrado via revisão visual dos screenshots (Playground DoD §6).
**Decisão:** Novo token `--backdrop` (e `--color-backdrop`), com o **mesmo valor** (`oklch(0.08 0 0 / 0.6)`) em ambos os temas — não segue o padrão dos demais tokens de superfície, que invertem entre dark/light.
**Motivo:** Overlays de modal convencionalmente escurecem o conteúdo por trás para dar foco ao diálogo, independentemente do tema ativo — um comportamento distinto de "tokens de superfície" que representam a UI normal.
**Impacto:** Nenhum nos tokens existentes; `--backdrop` é de uso exclusivo de `DialogOverlay`/`AlertDialogPrimitive.Overlay`.

### [2026-07-15] `suppressHydrationWarning` adicionado ao `<html>`
**Contexto:** O script anti-flash (Incremento 0.3) muda `data-theme` no DOM antes da hidratação do React, para evitar flash visual em quem prefere tema claro. Isso sempre gerou um warning de mismatch de hidratação no console do navegador — não detectado antes porque as validações anteriores só checavam o log do **servidor** (`next dev`), não o console do **navegador**. Só apareceu ao rodar Playwright com listener de console/pageerror, como o novo DoD exige.
**Decisão:** Adicionar `suppressHydrationWarning` ao elemento `<html>` em `layout.tsx`.
**Motivo:** É a técnica padrão (mesma usada por `next-themes`) para esse exato padrão de "script inline que muda um atributo do `<html>` antes da hidratação" — o warning é conhecido e esperado, não um bug real de conteúdo divergente.
**Impacto:** Nenhum efeito colateral: `suppressHydrationWarning` só silencia mismatches nos atributos do próprio elemento onde é aplicado, não em elementos filhos — não mascara bugs de hidratação reais no restante da árvore.

**Motivo:** Mesmo padrão já usado no 0.4b (Dialog+Modal, Toast+Toaster) — agrupar por afinidade temática, não um arquivo por seção/componente a qualquer custo.
**Impacto:** Nenhum na API — cada seção continua sendo um componente exportado e importado individualmente em `page.tsx`.

### [2026-07-15] Bug de build: `Button asChild` quebrava o Radix Slot
**Contexto:** Ao usar `<Button asChild><Link>...</Link></Button>` pela primeira vez (Header e Hero da Landing), o build falhou: "Slot failed to slot onto its children. Expected a single React element child." O componente `Button` sempre renderizava `{loading ? <Loader2/> : null}` seguido de `{children}` — quando `asChild` vira `Comp = Slot`, isso são 2 filhos, mas o Radix `Slot` exige exatamente 1. Nunca detectado antes porque todo uso anterior de `asChild` estava em *Trigger* de outro componente (`DialogTrigger asChild`, `TooltipTrigger asChild`), envolvendo um `<Button>` inteiro como filho único — o `Button` em si nunca tinha recebido `asChild` diretamente.
**Decisão:** `Button` agora renderiza `children` puro quando `asChild={true}`, e só inclui o wrapper de loading (`<>{loading...}{children}</>`) quando renderiza como `<button>` nativo.
**Motivo:** É o comportamento correto esperado pelo Radix Slot; loading + asChild não é uma combinação sensata de qualquer forma (um link não tem estado de loading próprio).
**Impacto:** Nenhuma quebra de API — `Button asChild` sem `loading` (o único uso real) continua funcionando; simplesmente deixou de quebrar o build.

### [2026-07-15] Screenshots `fullPage` precisam de scroll programático antes da captura
**Contexto:** A Landing usa scroll-reveal (`IntersectionObserver`) para fade-in de seções. As primeiras screenshots `fullPage` mostraram tudo abaixo de "Como funciona" completamente invisível (`opacity-0`). Investigação confirmou que usuários reais veem o reveal normalmente ao rolar — o problema é que o Playwright `page.screenshot({ fullPage: true })` não dispara scroll real antes de compor a imagem, então o `IntersectionObserver` nunca ativa para conteúdo abaixo da viewport inicial.
**Decisão:** Ajustar o **script de screenshot** (não o app) para rolar a página em passos incrementais antes de cada captura `fullPage`, em qualquer página com scroll-reveal.
**Motivo:** Era um falso positivo de bug de produto — na verdade um artefato do método de teste. Corrigir no lugar certo (harness de screenshot) evita relatórios de "bug" incorretos em sprints futuros com o mesmo padrão de animação.
**Impacto:** Nenhum no código do produto. Prática de screenshot documentada aqui para sprints futuros que usem `Reveal`/scroll-reveal.

### [2026-07-15] `users.id` = `auth.users.id` (FK explícita, sem `gen_random_uuid()` próprio)
**Contexto:** Padrão-ouro do Supabase para tabela de "profile": a tabela pública de usuário usa o mesmo UUID do `auth.users`, nunca gera um novo.

**Impacto:** O trigger existe (ponto de extensão pronto) mas está documentado como incompleto — qualquer um que reabrir esse arquivo já sabe que falta essa decisão, em vez de assumir que está pronto.

### [2026-07-15] Migrations e seeds validados localmente via Docker (Supabase CLI), sem projeto remoto
**Contexto:** Sem credenciais de um projeto Supabase real, mas o Supabase CLI local (`supabase db start`) sobe um Postgres real em Docker, permitindo validar schema/seed de verdade em vez de só revisar o SQL visualmente.

## Sprint 1.8b — Password Recovery

### [2026-07-17] `/reset-password` trata dois formatos de link de recuperação (PKCE e implicit grant)
**Contexto:** Ao testar `/reset-password` com um link de recovery real (gerado via Admin API para automação de teste), o link veio no formato `#access_token=...&type=recovery` (implicit grant, no fragmento da URL) em vez de `?code=` (PKCE). `@supabase/ssr` (usado em `packages/database`) não detecta esse formato automaticamente — ao contrário do `supabase-js` "puro", que faz auto-detecção de hash por padrão. Sem acesso a uma caixa de entrada real, não é possível confirmar com 100% de certeza qual formato o email de produção efetivamente entrega a um usuário real (a API Admin usada para gerar o link de teste pode não refletir exatamente o comportamento do fluxo `resetPasswordForEmail()` disparado por um client com `flowType: 'pkce'`).
**Decisão:** `apps/web/app/reset-password/page.tsx` trata os dois formatos: `?code=` via `exchangeCodeForSession()` e `#access_token=`/`#refresh_token=` via um novo `establishSessionFromHash()` em `use-auth.ts`, que lê o fragmento manualmente e chama `setSession()`. Depois de ler os tokens do hash, a URL é limpa (`history.replaceState`) para não deixar o token exposto na barra de endereço/histórico do navegador.
**Motivo:** Dada a incerteza sobre qual formato o email real vai entregar, e o custo baixo de suportar ambos, a escolha mais segura é não apostar em um único formato.
**Impacto:** Se no futuro ficar comprovado que só um formato ocorre na prática, o outro caminho pode ser removido — não é uma decisão definitiva, é uma proteção enquanto não há confirmação por teste real de email.

### [2026-07-17] Redirect URLs do Supabase precisam incluir `/reset-password` explicitamente (achado de infraestrutura)
**Contexto:** Testando o link de recovery real, o redirect caiu no domínio raiz configurado como Site URL do projeto (`aigamestudioos.com/`) em vez de `/reset-password`, mesmo com `redirectTo` corretamente enviado na chamada (confirmado inspecionando a própria URL de verificação gerada pelo Supabase, que continha `redirect_to=.../reset-password` no parâmetro). **Decisão:** Usuário adicionou ao Redirect URLs do projeto: `https://ai-game-studio-os-web.vercel.app/reset-password`, `https://aigamestudioos.com/reset-password` e `http://localhost:3000/reset-password` (dashboard-only, fora do meu alcance).

### [2026-07-17] Bootstrap de Studio via função `SECURITY DEFINER` (RPC), não via Server Action com admin-client
**Contexto:** Criar a primeira linha de `studios`/`users` para um usuário nunca pode passar pelas políticas RLS normais — elas são auto-referenciais (`studio_id = (select studio_id from users where id = auth.uid())`), então a subquery nunca resolve antes de a linha existir. Duas opções: (a) uma Server Action em `apps/web` usando `admin-client` (service role, bypassa RLS totalmente), ou (b) uma função Postgres `SECURITY DEFINER`, chamada via RPC pelo client normal.
**Decisão:** Função `SECURITY DEFINER` (`bootstrap_studio_for_current_user`), definida em `supabase/migrations/20260717000001_bootstrap_studio.sql`, `grant execute` só para `authenticated`.
**Motivo:** Escopo muito mais estreito e auditável — a função só pode criar a estrutura do PRÓPRIO `auth.uid()` chamador, nunca aceita um `user_id`/`studio_id` arbitrário. Usar `admin-client` em uma Server Action exigiria confiar que o código da action nunca aceita parâmetros que permitam criar/alterar dados de outro usuário — um único bug ali teria alcance total do banco (service role bypassa RLS em qualquer tabela). A função no banco é uma superfície de ataque muito menor.
**Impacto:** Qualquer operação privilegiada futura semelhante (aceitar convite, transferir posse de Studio) deveria seguir o mesmo padrão — função `SECURITY DEFINER` com escopo mínimo, não Server Action com admin-client, a menos que exista razão concreta para preferir a segunda.

### [2026-07-17] Bug real: recursão infinita nas políticas RLS do Sprint 1.7 (nunca detectado antes)
**Contexto:** Testando o bootstrap contra Postgres real (Docker local), toda tentativa de `select`/`insert` em `users`/`studios` sob um usuário autenticado de verdade falhava com "infinite recursion detected in policy for relation users". Causa: as 27 políticas `*_isolation` criadas no Sprint 1.7 usam `studio_id = (select studio_id from users where id = auth.uid())` — essa subquery lê da própria tabela `users` (RLS habilitado), reacionando a mesma política recursivamente. A validação do Sprint 1.7 só conferiu `pg_class.relrowsecurity = true` (RLS ligado), nunca testou uma política de verdade sob autenticação real — por isso o bug sobreviveu sem ser notado por um sprint inteiro.
**Decisão:** `supabase/migrations/20260717000002_fix_rls_recursion.sql` cria `current_user_studio_id()` (função `SECURITY DEFINER`, bypassa RLS internamente) e recria as 27 políticas usando essa função em vez da subquery direta.
**Motivo:** É o fix padrão documentado pelo próprio Supabase para esse padrão de erro — mover a leitura auto-referencial para uma função que roda com o privilégio do dono, quebrando o ciclo.
**Impacto:** Qualquer política de RLS futura que precise "olhar para a própria linha do usuário" deve usar `current_user_studio_id()`, nunca repetir a subquery direta em `users`.

### [2026-07-17] Bug real: nenhum GRANT de tabela para o role `authenticated` (Sprint 1.7)
**Contexto:** Depois de corrigir a recursão, toda query autenticada ainda falhava — agora com "permission denied for table X". Causa: nenhuma migration do Sprint 1.7 concedeu privilégios de tabela (`GRANT SELECT/INSERT/UPDATE/DELETE`) ao role `authenticated`. RLS é avaliado *depois* do GRANT de tabela no Postgres — sem o GRANT, RLS nunca chega a ser considerado.
**Decisão:** `supabase/migrations/20260717000003_grant_authenticated_privileges.sql` concede `select, insert, update, delete on all tables in schema public to authenticated`, mais `alter default privileges` para que tabelas de migrations futuras herdem o mesmo grant automaticamente.
**Motivo:** RLS continua sendo o controle de acesso real (`ADR-003`) — o GRANT é só o portão de baixo nível que o Postgres exige antes de RLS entrar em cena; sem ele, nenhuma política (por mais correta que fosse) teria efeito.
**Impacto:** Nenhuma migration futura de nova tabela precisa lembrar de conceder isso de novo — `alter default privileges` cobre automaticamente.

### [2026-07-17] Projeto Supabase remoto nunca tinha o schema do Sprint 1.7 aplicado
**Contexto:** Ao tentar aplicar as 3 migrations novas via SQL Editor, erro `relation "public.users" does not exist` revelou que as 9 migrations do Sprint 1.7 nunca foram aplicadas ao projeto remoto — desde sua criação (Sprint 1.8a), ele só serviu para Auth (recurso nativo do Supabase, não depende de migrations), nunca para o schema de negócio. Adicionalmente, o projeto estava pausado (comum no free tier após inatividade), o que inicialmente pareceu um problema de DNS.

**Motivo:** `db push` aplica migrations em ordem e registra o que já rodou — evita o risco de pular uma migration ou aplicá-la fora de ordem, que colar manualmente no SQL Editor não protege contra.
**Impacto:** A partir de agora, o projeto remoto tem o schema completo. Qualquer nova migration deve ser aplicada via `supabase db push` (ou equivalente rastreado), não colada manualmente — o SQL Editor manual deve ser reservado para inspeção/debug, não para aplicar schema.

### [2026-07-27] Singleton do browser client extraído para `apps/web/lib/supabase-client.ts`
**Contexto:** `use-current-studio.ts` (Studio settings) precisa do mesmo client Supabase que `use-auth.ts` já mantém como singleton em módulo — duplicar a declaração criaria uma segunda instância de `GoTrueClient` (aviso "Multiple GoTrueClient instances detected", já evitado desde o Sprint 1.8a).

## Sprint 1.8d-3 — Convites

### [2026-07-28] Convite usa `auth.admin.inviteUserByEmail` (Server Action) em vez de mecanismo próprio de token/email
**Contexto:** Nenhuma tabela de "convites" existia no schema; precisava desenhar do zero como enviar e aceitar um convite. Opção A: sistema próprio (token gerado, tabela de tokens, envio de email via serviço externo/Edge Function). Opção B: usar o mecanismo nativo do Supabase Auth (`admin.inviteUserByEmail`), que já cria o `auth.users` não confirmado e envia o email com link mágico usando o template de Auth do projeto.
**Decisão:** Opção B. `apps/web/app/settings/studio/actions.ts` é uma Server Action (primeira do projeto) que usa `admin-client` (service role) só para essa chamada — o resto (ler a sessão do chamador, criar o registro do convite) usa `server-client` normal, sujeito a RLS.
**Motivo:** Reimplementar envio de email + geração/validação de token seria refazer algo que o Supabase Auth já resolve corretamente (inclusive segurança do token, expiração, rate limiting). `inviteUserByEmail` é inerentemente admin-only — não existe alternativa client-side, então usar `admin-client` aqui é a mesma categoria de exceção já registrada para `bootstrap_studio_for_current_user` (escopo mínimo e auditável).
**Impacto:** O redirect do link de convite aponta para `/reset-password` (mesma página usada para recuperação de senha) — os dois fluxos do Supabase (`invite` e `recovery`) chegam no mesmo formato de link (`?code=` ou `#access_token=`), e a página já trata os dois (ver decisão do Sprint 1.8b). Nenhuma tela nova de "definir senha inicial" foi necessária.

### [2026-07-28] Bootstrap estendido para reconhecer convite pendente antes de criar Studio novo
**Contexto:** O bootstrap do Sprint 1.8d-1 sempre criava um Studio novo para qualquer usuário sem profile. Com convites, isso precisa mudar: um email convidado deve entrar no Studio convidante, não ganhar um Studio próprio.
**Decisão:** `bootstrap_studio_for_current_user` (recriada via `create or replace function` em `20260728000001_invites.sql`, forward-only) agora busca um convite `pending` para o email do usuário antes de decidir; se encontrar, entra nesse Studio com o papel do convite (criando a Role se ainda não existir no Studio) e marca o convite como `accepted`. Só cria Studio novo se não houver convite.
**Motivo:** Manter um único ponto de entrada ("o que acontece no primeiro login") em vez de duas lógicas paralelas (uma para bootstrap normal, outra para aceite de convite) que a UI precisaria escolher entre si.
**Impacto:** Qualquer fluxo futuro que precise "adicionar alguém a um Studio existente no primeiro login" (ex.: convite por link compartilhável, não só email) deve seguir o mesmo padrão — inserir a intenção numa tabela e deixar o bootstrap resolver, não criar um novo caminho de entrada.

### [2026-07-28] Erros de `inviteUserByEmail` tratados por `.code`, com distinção real entre "já convidado" e "conflito de conta"
**Contexto:** Testando o fluxo de reenvio de convite (cancelar e convidar de novo o mesmo email), `inviteUserByEmail` retorna `email_exists` tanto para (a) alguém que já tem conta de verdade em outro Studio quanto para (b) alguém que já foi convidado antes e ainda não aceitou (só tem `auth.users`, sem `public.users`). Tratar os dois da mesma forma (erro) bloquearia reenvios legítimos; tratar os dois como sucesso esconderia conflitos reais. Também descoberto nesse processo: o projeto está sob rate-limit real de envio de email (`over_email_send_rate_limit`) por uso intenso de teste — a primeira versão do código tratava QUALQUER erro (incluindo rate-limit) da mesma forma que "já convidado", mascarando o rate-limit como sucesso silencioso.
**Decisão:** Branch por `error.code` (não por substring de `.message`, que o Supabase não garante formatar de forma estável): `over_email_send_rate_limit` → mensagem amigável + revoga o convite (nenhuma conta foi criada, ficaria órfão); `email_exists` → consulta `public.users` pelo email — se existir profile, é conflito real (revoga + erro); se não existir, é reenvio a alguém já convidado (mantém o convite pendente, sem erro). Qualquer outro código → revoga + erro genérico.
**Motivo:** Mascarar um rate-limit real como sucesso é pior do que mostrar o erro — o usuário acharia que o convite foi enviado quando na verdade nenhuma conta/email foi criado. Distinguir os dois motivos de `email_exists` evita tanto bloquear reenvios legítimos quanto ocultar conflitos reais de conta.
**Impacto:** Já usado como precedente: `apps/web/hooks/use-auth.ts` (`mapAuthError`) já seguia esse princípio para outros fluxos de Auth — esta decisão reforça o padrão "sempre branch por `.code`, nunca por texto de mensagem" para qualquer novo tratamento de erro do Supabase Auth.

### [2026-07-28] Metodologia de teste ajustada: parar de disparar envio real de email em testes repetidos
**Contexto:** Supabase enviou um aviso de alta taxa de bounce no projeto `vkyswyuxitwakjqjteso`, com risco de restrição de envio. Causa: testes desta sessão (Sprints 1.8b, 1.8d-3) chamaram repetidamente `inviteUserByEmail`/`resetPasswordForEmail` — que **enviam email de verdade** — usando endereços fictícios `@aigamestudioos.com` sem caixa de entrada real, gerando bounce a cada chamada.
**Decisão:** Testes automatizados passam a usar `admin.generateLink()` (gera o link de ação sem despachar email de verdade) como caminho padrão de validação. Os caminhos que enviam email real (`inviteUserByEmail`, `resetPasswordForEmail`) só são exercitados no máximo uma vez por sprint, para confirmar que a integração funciona — nunca em loop de depuração.
**Motivo:** `generateLink` valida exatamente a mesma lógica de backend (criação de `auth.users`, geração do link, formato do redirect) sem o efeito colateral de enviar/bouncing emails reais. Repetir o envio real dezenas de vezes durante depuração não agrega validação adicional proporcional ao risco à reputação de envio do projeto.
**Impacto:** Scripts de teste futuros (`*-test.mjs` no scratchpad) devem preferir `generateLink` por padrão; qualquer teste que precise do envio real deve ser sinalizado explicitamente como tal e executado com moderação.

## Sprint 1.8d-4 — Papéis e permissões reais

### [2026-07-29] Enforcement via RLS (WITH CHECK), não checagem client-side/Server Action
**Contexto:** Precisava decidir onde impor "só Owner/Admin pode convidar, só Owner pode editar Studio": (a) só na UI (esconder botões) + checagem na Server Action; ou (b) na própria política de RLS da tabela, via `WITH CHECK`.
**Decisão:** RLS é a camada real de enforcement (`invites_insert`/`invites_update`/`studios_update` com `current_user_has_permission(...)` no `WITH CHECK`). A Server Action e a UI também checam (mensagem amigável antecipada), mas são conveniência de UX, não a proteção real.
**Motivo:** Qualquer checagem só em código de aplicação pode ser contornada por quem chama a API do Supabase diretamente (a `anon`/`publishable` key é pública no bundle do cliente). RLS é reforçado pelo próprio Postgres, não tem como contornar sem a service role key. Confirmado por teste direto: um Member tentando `insert`/`update` diretamente via `supabase-js` (não pela UI) é bloqueado do mesmo jeito.
**Impacto:** Qualquer novo recurso que precise de controle de acesso por papel deve seguir o mesmo padrão — política de RLS com `current_user_has_permission()`, não só lógica de aplicação. A UI/Server Action ficam livres para dar mensagens mais amigáveis, mas nunca são a única barreira.

### [2026-07-29] Três papéis pré-criados na criação do Studio (Owner/Admin/Member), não só sob demanda
**Contexto:** Convites (1.8d-3) já criavam uma Role sob demanda se ela não existisse ainda para o Studio (só "Member" até então). Com permissões reais, criar uma Role "Admin" sob demanda no momento do aceite exigiria decidir ali, na hora, quais permissões ela deveria ter — lógica espalhada em dois lugares (criação do Studio vs. aceite de convite).
**Decisão:** Os 3 papéis (Owner, Admin, Member) e seus `role_permissions` são criados de uma vez na criação do Studio (dentro de `bootstrap_studio_for_current_user`, ramo "sem convite"). O aceite de convite só faz `select` do papel já existente pelo nome — o fallback de criar sob demanda (sem nenhuma permissão) só cobre Studios criados *antes* desta migration.
**Motivo:** Centralizar "o que cada papel pode fazer" em um único lugar (a criação do Studio) evita que a resposta mude dependendo de quando/como o papel foi criado.
**Impacto:** Qualquer novo papel padrão (se houver um dia) deve ser adicionado no mesmo bloco do bootstrap, não em um novo ponto de criação sob demanda.

### [2026-07-29] Catálogo de permissões pequeno e ligado a ações que já existem, não especulativo
**Contexto:** Poderia ter sido tentador popular `permissions` com um catálogo amplo antecipando funcionalidades futuras (Projects, Games, Billing, etc.).
**Decisão:** Só 3 permissões: `studio.edit`, `studio.invite_members`, `studio.manage_members` — exatamente as 2 ações que existem hoje na UI (editar Studio, convidar/cancelar convite).
**Motivo:** Permissões sem nenhuma política de RLS as consultando são só entradas mortas na tabela — pior que não ter nada, porque parecem implementadas sem estar. Adicionar antecipadamente também arrisca errar o nome/granularidade antes de saber como a funcionalidade real vai precisar checar isso.
**Impacto:** Quando Projects/Games/etc. ganharem controle de acesso por papel (Sprint 2.0+), adicionar a permissão específica + a política de RLS correspondente na mesma migration — nunca uma sem a outra.

## Sprint 2.2 — Knowledge real

### [2026-07-29] Bug real: `createVersion()` omitia campos de auditoria obrigatórios (encontrado antes de testar)
**Contexto:** `packages/database/src/repositories/knowledge-documents-repository.ts`'s `createVersion()` existia desde o Sprint 1.7, com assinatura `Pick<KnowledgeDocumentVersionsRow, "studio_id"|"document_id"|"version_number"|"content">`. `created_actor_type` é `NOT NULL` sem default na tabela `knowledge_document_versions` — a assinatura do repository nunca exigia esse campo, então qualquer chamador seguindo o tipo TypeScript literalmente teria uma inserção falhando por violação de NOT NULL.

## Sprint 2.4/2.5 — Release Pipeline

### [2026-08-04] Releases não têm `platform_id` — a plataforma vive na Submission, não no Release
**Contexto:** O pedido original do Release Pipeline sugeria um `target_store` no Release. `submissions.platform_id` já existe desde o schema original (Sprint 1.7), e `submissions.release_id` é N:1 com `releases` — ou seja, um Release já pode gerar Submissions para lojas diferentes.
**Decisão:** Não adicionar `platform_id`/`target_store` a `releases`. `release_channel` (Internal/Alpha/Beta/Production) foi adicionado normalmente — é atributo do Release, não da loja.
**Motivo:** Duplicar a plataforma no Release contradiria a relação N:1 já modelada e violaria "nenhuma duplicação de dados".
**Impacto:** O formulário de criação de Submission em Publishing pede Release + Plataforma separadamente, derivando a Build correta a partir dos dois.

### [2026-08-04] Simulação de Build travada: reaproveitar a mesma linha (Retry), não criar uma tabela de "tentativas"
**Contexto:** Sem CI/CD real, o progresso de Build é simulado por `setTimeout` no client — se a aba fechar/recarregar no meio, a Build fica presa em `RUNNING` para sempre, sem nada no servidor para completá-la (achado durante a validação do Golden Path do Sprint 2.5, não hipotético).
**Decisão:** `isBuildStuck()` (limite `BUILD_SIMULATION_STUCK_THRESHOLD_MS = 20s`, centralizado em `apps/web/lib/build-simulation.ts`) identifica a Build travada na UI; "Retry Build" reaproveita a mesma linha (`buildsRepo.update()` volta o status para `PENDING`), registrando `BuildFailed` (não apaga o histórico de que a tentativa anterior travou) seguido de `BuildRetried`, e reinicia a mesma simulação.
**Motivo:** O schema não tem um conceito de "tentativa"/"attempt" separado da Build — criar uma nova linha a cada retry duplicaria `build_number` sem necessidade e fragmentaria o histórico em várias linhas para o que é conceitualmente uma única Build. Reaproveitar a linha, com os dois eventos marcando a falha e o retry, preserva auditoria sem exigir decisão de schema nova.
**Impacto:** Se no futuro builds precisarem de um histórico de tentativas explícito (ex.: métricas de flakiness de CI real), isso vira uma decisão de schema própria — não decidida aqui.

### [2026-08-04] Débitos técnicos registrados, não corrigidos neste sprint (aprovados explicitamente pelo usuário para o backlog)
**Contexto:** Revisão do Sprint 2.5 apontou três pontos que funcionam para o MVP mas não escalam bem.
**Decisão:** Documentar, não bloquear o sprint:
1. `build_number` é calculado por contagem no client (`use-game-version.ts`, `createBuild()`) — duas criações simultâneas para a mesma Version/Platform podem gerar o mesmo número. Correção futura: calcular de forma transacional no banco (sequência ou `SELECT ... FOR UPDATE`/função Postgres).
2. `artifact_url` aponta para `builds.aigamestudioos.local/mock/...` — um artefato inexistente. A UI já rotula o checksum como "(simulado)"; reforçar isso se um link/botão de download real do `artifact_url` for adicionado no futuro, para nunca parecer um download real.
3. `usePublishableReleases` (Publishing → New Submission) resolve Release→Version→Game→Builds em consultas separadas por Release, um padrão N+1. Funciona no volume atual (poucas Releases); revisar para uma consulta única/view/RPC quando o volume justificar.
**Motivo:** Nenhum dos três é um bug — são limitações conhecidas de um MVP que ainda não tem volume ou concorrência reais. Consertar agora seria otimização prematura sem sinal de que é necessário.
**Impacto:** Repetido aqui e em `IMPLEMENTATION_LOG.md` para não virar dívida invisível — releitura futura desses dois arquivos deve encontrar os três pontos.

## Sprint 2.5.1 — Production Readiness

### [2026-08-04] Migrations em produção continuam manuais — scriptadas e com gate, não automatizadas via CI
**Contexto:** O Sprint 2.5 revelou que uma migration validada localmente (Sprint 2.4) nunca chegou ao Supabase de produção, e nada no processo detectava isso antes do Golden Path de produção esbarrar num erro real (`PGRST204`). A correção óbvia seria um pipeline de CI que rodasse `supabase db push` automaticamente a cada push com migration nova.
**Decisão:** Não construir esse pipeline agora. Em vez disso: `scripts/check-schema-sync.sh` (compara local×remoto, falha explicitamente se houver divergência ou se faltar credencial) + um checklist obrigatório em `DEPLOY_RUNBOOK.md` + um gate formal em `DEFINITION_OF_DONE.md` §10 que impede declarar um sprint com migration "Concluído" sem os 4 itens do checklist marcados.
**Motivo:** Instrução explícita do usuário — para um solo founder, o custo de manter um pipeline de CI/CD completo (secrets geridos, jobs, superfície de coisas que podem quebrar) supera o valor neste estágio, quando o volume de sprints com mudança de schema ainda é baixo. Um script + checklist resolve a causa raiz real (ninguém verificava o estado antes de seguir em frente) sem essa complexidade adicional.
**Impacto:** Se o ritmo de sprints com schema crescer a ponto do passo manual virar gargalo mensurável (não hipotético), a evolução natural é automatizar só esse step (`supabase db push` num job de CI), reaproveitando o mesmo script de verificação — não reconstruir o processo do zero.

## Sprint 2.7 — Gerenciar membros existentes

### [2026-08-05] Remoção de membro é soft-delete (`archived_at`), nunca apaga a conta de `auth.users`
**Contexto:** "Remover um membro" poderia significar deletar a conta de autenticação (`admin.auth.admin.deleteUser()`) ou só revogar o acesso ao Studio.
**Decisão:** `users.archive()` só marca `archived_at`/`archived_actor_type`/`archived_actor_id` — mesmo padrão de soft-delete já usado em todo o schema (`AGSOS-SPEC-003` §1). A linha de `user_roles` correspondente também é removida (via troca de papel/DELETE), então o membro arquivado perde acesso de fato (RLS de todas as tabelas de negócio depende de `current_user_studio_id()`, que lê `users.studio_id` — um usuário arquivado ainda tem `studio_id`, mas sem nenhuma role/permissão ativa não consegue mais escrever nada, e pode ser reavaliado no futuro).
**Motivo:** Deletar a conta de auth é destrutivo e difícil de reverter (login, histórico de `created_actor_id` em outras tabelas ficaria órfão). Soft-delete é reversível (reativar = desarquivar + reatribuir role) e consistente com o resto do projeto.

**Contexto:** Ao planejar a UI de troca de papel/remoção, notei que `users_isolation`/`user_roles_isolation` (desde o Sprint 1.7) só verificavam `studio_id`, sem nenhuma permissão — diferente de `invites`/`studios`, que já ganharam `studio.manage_members`/`studio.edit` no Sprint 1.8d-4. Isso significava que qualquer membro do Studio já podia, tecnicamente, fazer UPDATE/DELETE na linha de `users`/`user_roles` de qualquer outro membro (inclusive o Owner) — só não havia UI que exercitasse esse caminho de escrita ainda.
**Decisão:** Fechado via `20260805000001_member_management_permissions.sql` antes de escrever qualquer linha de UI — a permissão de gravação nunca existiu exposta na prática (nenhuma UI a usava), mas o buraco no banco existia desde o Sprint 1.7.
**Motivo:** Corrigir a causa (RLS) antes do sintoma (UI) — construir a UI de gerenciamento de membros sobre uma RLS sem gate teria tornado esse achado explorável de fato pela primeira vez, não só teoricamente.
**Impacto:** Vale uma auditoria futura das demais tabelas com política `*_isolation` genérica (sem gate de permissão) para checar se alguma outra também devia ter um `studio.*` específico e não tem — não feita neste sprint (fora de escopo, mas registrada como sugestão). **Nota do Sprint 2.8:** essa auditoria sugerida encontrou exatamente esse padrão em `store_connections` também — corrigido no mesmo sprint que a descobriu, ver abaixo.

## Sprint 2.8 — Store Connections (backend)

### [2026-08-06] `credentials_ref` (ponteiro) mantido; Vault implementado, `encrypted_credentials` não foi criado
**Contexto:** O pedido original especificava um campo `encrypted_credentials`. A auditoria de Fase 1 encontrou que `store_connections.credentials_ref` já existe desde `20260716000006_publishing.sql`, com o comentário original *"referência a Supabase Secrets; nunca a credencial em si"* — mesmo texto em `DATA_MODEL.md`, citando `AGSOS-SPEC-004 §13`. Essa é uma decisão de arquitetura já tomada (padrão de ponteiro, não criptografia embutida na própria linha), só nunca implementada.
**Decisão:** Não criar `encrypted_credentials`. Implementado o mecanismo que faltava com **Supabase Vault** (`create extension supabase_vault`) — `credentials_ref` guarda o UUID do segredo no Vault, nunca o segredo. Uma função `set_store_connection_secret()` (SECURITY DEFINER) é o único caminho de escrita, validando posse do Studio + permissão antes de tocar `vault.*`.
**Motivo:** Adicionar uma coluna paralela para o mesmo propósito contradiria uma decisão já congelada e documentada, além de criar dois padrões concorrentes para a mesma coisa no mesmo schema.
**Impacto:** Qualquer integração futura que precise guardar um segredo (ex.: tokens de outras integrações de `AGSOS-SPEC-008`) tem, a partir de agora, um exemplo real e testado de como usar Vault neste projeto — não precisa reinventar.

### [2026-08-06] Chamadas às APIs Apple/Google adiadas para `packages/integrations/` (Sprint 2.9), não implementadas em Server Actions
**Contexto:** `AGSOS-SPEC-008` (frozen) já especifica Adapter Pattern obrigatório para toda integração externa (`IntegrationAdapter.connect()/disconnect()/health()`), com pasta dedicada por provider. `packages/integrations` já existe no monorepo, buildável, mas vazio.
**Decisão:** Este sprint (2.8) não chama nenhuma API externa — só schema/RLS/Vault/repository. As chamadas reais (`listApps()` da Apple/Google para o botão "Validate Connection") ficam para o Sprint 2.9, dentro de `packages/integrations/{apple,google-play}/`.
**Motivo:** Implementar a chamada ad hoc numa Server Action teria funcionado no curto prazo, mas ignorado uma decisão de arquitetura já congelada — e o "lugar certo" (pacote) já existe, só precisa ser preenchido.
**Impacto:** Nenhum ainda — Sprint 2.9 é quem paga esse custo, com o benefício de todo adapter futuro (RevenueCat, PostHog, etc., já listados em `AGSOS-SPEC-008 §4`) seguir o mesmo contrato testado uma vez.

### [2026-08-06] Remoção de Store Connection é DELETE real, não soft-delete (provisório)
**Contexto:** O resto do projeto usa soft-delete (`archived_at`) consistentemente. Store Connections tem um motivo a mais para isso: o segredo no Vault precisa ser limpo em algum momento, e a trigger criada neste sprint limpa no DELETE.

**Motivo:** Sem UI nesta sprint, não há uma decisão de produto ainda sobre se "remover" deveria ser reversível (arquivar, permitir reconectar mantendo o segredo) ou definitivo. Manter DELETE real é mais simples e não fecha porta nenhuma — soft-delete pode ser adicionado depois sem quebrar o que existe.
**Impacto:** Sprint 2.10 (UI) deve decidir isso explicitamente antes de expor um botão "Remover" — se a decisão for soft-delete, a trigger de limpeza do Vault precisa ser revista (não pode disparar num archive). **Atualização do Sprint 2.9:** a UI foi construída mantendo DELETE real (botão "Remover") — a decisão acima foi confirmada, não revertida, já que a UI trouxe um botão "Disconnect" separado (limpa a credencial, mantém a linha) que cobre o caso reversível sem precisar de soft-delete na linha inteira.

## Sprint 2.9 — Apple App Store Connect (infraestrutura da integração completa)

### [2026-08-06] Sem credenciais Apple reais disponíveis — sprint entrega infraestrutura completa, nunca simula sucesso
**Contexto:** Instrução explícita do usuário: se não houver conta Apple Developer com API habilitada, o sprint deve parar na validação com credenciais reais, documentando a lacuna — nunca simular um resultado de sucesso não verificado.
**Decisão:** Toda a infraestrutura (adapter, JWT, Vault, RLS, UI, eventos) foi implementada e testada com o máximo de realismo possível — a chamada de rede é real, contra a API real da Apple (`api.appstoreconnect.apple.com`), só a credencial em si é fabricada (uma chave EC P-256 sintaticamente válida, mas não uma credencial Apple de verdade). O caminho de sucesso (`listApps()` retornando Apps reais) fica documentado como não verificado, não como "concluído".
**Motivo:** Declarar sucesso sem verificação real seria pior do que documentar a lacuna — o usuário explicitamente pediu para nunca "simular sucesso ou construir soluções alternativas fora da arquitetura".
**Impacto:** Assim que uma credencial Apple real existir, validar `listApps()` com ela é o primeiro passo — não deveria exigir nenhuma mudança de código, só uma credencial de verdade.

### [2026-08-06] Vocabulário padrão para relatar sprints de integração sem credencial real: "transporte" vs. "funcional"
**Contexto:** O relatório inicial deste sprint chamou o resultado de "integração real" — tecnicamente verdadeiro (a chamada de rede é real, contra a Apple real), mas ambíguo: dá a entender que `listApps()`/parsing de resposta/paginação/rate limit já foram provados, quando só DNS/TLS/JWT/endpoint/autenticação/tratamento de erro foram.
**Decisão:** A partir de agora, todo sprint de integração externa sem credencial real classifica o resultado em duas categorias separadas, nunca uma frase só: **"integração de transporte validada"** (conectividade, protocolo, autenticação, erro — provado contra o provedor real, mesmo com credencial fabricada) vs. **"integração funcional pendente"** (resposta de sucesso real, parsing, paginação, casos de borda — só provável com uma credencial verdadeira). Títulos de sprint/seção usam "infraestrutura da integração completa", não "integração real", enquanto a validação funcional estiver pendente.
**Motivo:** Precisão de relato — a diferença entre "provamos que conseguimos falar com a Apple" e "provamos que conseguimos usar a Apple" é pequena na frase, mas grande na certeza que ela transmite.
**Impacto:** Aplicar este vocabulário em todo sprint futuro de integração (Google Play, Steam, RevenueCat, etc.) que não tiver credencial real disponível no momento do teste.

### [2026-08-06] `get_store_connection_secret()` — GRANT só para `service_role`, nunca `authenticated`
**Contexto:** Diferente de `set_store_connection_secret()`/`clear_store_connection_secret()` (Sprint 2.8/2.9, ambas com checagem de posse/permissão internas E grant para `authenticated`), a função que LÊ o segredo de volta não pode ser chamável por nenhum usuário autenticado comum — devolver o segredo em texto puro pela API violaria "nunca retornar secrets pelas APIs", mesmo que a função checasse posse/permissão internamente.
**Decisão:** `revoke execute ... from public; grant execute ... to service_role;` — só chamável a partir de uma Server Action usando `admin-client.ts`. Testado: nem o Owner autenticado da própria Store Connection consegue chamar essa função.
**Motivo:** A segurança de "nunca expor um segredo" não deveria depender de uma checagem de lógica de negócio que poderia ter um bug — deve ser estruturalmente impossível de alcançar pelo caminho errado.
**Impacto:** Todo mecanismo futuro de leitura de segredo (Google Play, outras integrações de `AGSOS-SPEC-008`) deveria seguir o mesmo padrão: grant restrito a `service_role`, nunca a `authenticated`, mesmo com checagem interna. **Atualização crítica do Sprint 2.9.1:** essa decisão estava certa na intenção, mas a implementação (`revoke ... from public`) não bastou em produção — ver decisão abaixo.

### [2026-08-07] `revoke ... from public` não fecha o gap em produção — GRANTs a `anon`/`authenticated` são diretos, não via `PUBLIC`
**Contexto:** Validando produção de verdade pela primeira vez (Sprint 2.9.1), uma chamada REST anônima real contra `get_store_connection_secret()` executou sem erro de permissão — a função projetada para ser exclusiva de `service_role` estava, na prática, chamável por `anon`. `set_store_connection_secret()`/`clear_store_connection_secret()` também tinham `anon` de sobra (deveriam ter só `authenticated`+`service_role`).
**Causa raiz:** o projeto Supabase de produção concede `EXECUTE` em função nova diretamente às roles nomeadas `anon`/`authenticated`/`service_role` (privilégio padrão do projeto), não ao pseudo-role `PUBLIC`. `revoke ... from public` nunca tocou esses grants nomeados. **O Postgres local não reproduz esse comportamento** — a mesma função já ficava corretamente restrita localmente, sem ajuste nenhum, o que fez a lacuna passar despercebida em toda a validação local extensa do Sprint 2.9 (9/9 checks, incluindo o teste explícito que o Owner autenticado não conseguia chamar a função).
**Decisão:** `revoke execute ... from anon, authenticated` explícito (não só `public`) em toda função `SECURITY DEFINER`, aplicado via `20260807000002_store_connection_secret_grants_fix.sql` no mesmo ciclo em que o gap foi descoberto — sem esperar um sprint novo, dado que é uma correção de segurança. Confirmado corrigido com uma nova chamada REST anônima (`401` nas três funções).
**Motivo:** Testar só localmente não detecta esse tipo de divergência de configuração entre ambientes — só uma chamada real contra produção revela o `GRANT` de fato em vigor.
**Impacto:** Regra permanente registrada em `DEPLOY_RUNBOOK.md` §11: toda função `SECURITY DEFINER` nova leva `revoke ... from anon, authenticated` explícito, e o gate de segurança só é considerado fechado depois de uma chamada REST anônima real contra produção confirmando o bloqueio — não antes. Recomendado (não feito nesta sessão, fora do escopo pedido) auditar os `GRANT`s de todas as funções `SECURITY DEFINER` já existentes em produção para o mesmo padrão.

### [2026-08-06] Bug pré-existente descoberto: Studio seedado (`founder@aigamestudio.os`) nunca teve nenhuma permission
**Contexto:** Achado ao tentar criar a primeira Store Connection localmente com a conta usada em quase toda validação deste projeto — bloqueado pela RLS. Causa raiz: o Studio seedado foi criado antes do sistema de roles/permissions existir (Sprint 1.7) e nunca recebeu backfill de `role_permissions`, diferente de todo Studio real (criado via `bootstrap_studio_for_current_user()`, que já concede tudo ao Owner).
**Decisão:** Corrigido nos dois arquivos de seed (`seed.sql` e `seed/02_demo_studio.sql`) — Owner do Studio seedado agora recebe todas as permissions existentes, mesma lógica do bootstrap real.
**Motivo:** Sem isso, toda validação local futura com a conta `founder` continuaria falhando silenciosamente em qualquer RLS com gate de permissão, um risco de "não simular sucesso por acidente" (um teste que falha por engano de setup, não por um bug real, é tão perigoso quanto simular sucesso).
**Impacto:** **Não afeta produção** — nenhum Studio real foi criado por esse caminho, todos vêm do bootstrap real. Documentado também como achado de bug em `IMPLEMENTATION_LOG.md`, com a descoberta adicional de que `supabase/seed.sql` (o arquivo que a CLI de fato lê) precisa ser editado manualmente além do `seed/*.sql` "fonte" — não existe script de regeneração automática (débito técnico registrado).

### [2026-08-08] Framework compartilhado de adapters (`packages/integrations/src/core/`) em vez de duplicar o Apple Adapter para o Google
**Contexto:** Instrução explícita do usuário antes de iniciar o Sprint 2.10: não copiar o Apple Adapter para criar o do Google Play — extrair tudo que é comum (contrato de adapter, tratamento de erro, fetch com timeout) em componentes compartilhados, para que providers futuros (Steam, Microsoft, Nintendo, RevenueCat) reusem um framework real.
**Decisão:** Criado `packages/integrations/src/core/{types,http,errors}.ts` com `IntegrationAdapter`/`HealthResult`/`ListResult<T>`/`ItemResult<T>`, `fetchJson()` (fetch+timeout único) e sanitização de erro genérica por status HTTP. O Apple Adapter (Sprint 2.9) foi retrofitado sobre esse framework no mesmo sprint, sem mudança de comportamento — só para não deixar o `core/` sem nenhum consumidor validado além do próprio Google.
**Motivo:** Um segundo provider construído do zero é a última chance barata de descobrir o que era genuinamente comum vs. específico de um provider — esperar um terceiro provider para refatorar custaria mais.
**Impacto:** Todo adapter futuro de `AGSOS-SPEC-008` deveria implementar `IntegrationAdapter` e reusar `fetchJson()`/`sanitizeHttpError()` do `core/`, só sobrepondo mensagens de erro específicas do seu provider — não reimplementar timeout/contrato do zero.

### [2026-08-08] Google Play "Validate Connection" via criar+apagar um draft edit, não uma `listApps()` — limitação real da API, não uma escolha de design
**Contexto:** Ao planejar o Sprint 2.10 nos mesmos moldes do Apple (`GET /v1/apps` lista todos os apps do time), descobriu-se que a Android Publisher API v3 não tem nenhum endpoint equivalente — todo recurso vive sob `applications/{packageName}/...`, exigindo o package name de antemão. Ajuste de design proposto e confirmado pelo usuário antes de implementar (`AskUserQuestion`).
**Decisão:** Campo "Package Name" obrigatório na credencial Google (não existe para a Apple). "Validate Connection" prova acesso criando um draft edit (`POST .../edits`) e apagando-o imediatamente (`DELETE .../edits/{id}`) — nunca deixando um edit pendurado no Play Console. `listApps()` do adapter, quando a validação passa, retorna um único item com `id`/`name`/`packageName` iguais ao package name configurado, já que a API também não expõe o nome de exibição do app por nenhum endpoint simples.
**Motivo:** Melhor um fluxo de validação real e honesto sobre o que a API do Google de fato permite do que fabricar uma `listApps()` que não existe de verdade nessa API.
**Impacto:** A UI de Store Connections trata "apps descobertos" da Google como sempre 1 item (o configurado), diferente da Apple onde pode ser vários — comportamento documentado no código (`google-play/types.ts`), não um bug a corrigir depois.

### [2026-08-09] Evento operacional (`StoreConnectionCallCompleted`) é uma categoria separada de evento de domínio, nunca fundida
**Contexto:** Ao planejar o Sprint 2.10.1, os eventos de domínio já existentes (`StoreConnectionValidated`, `StoreConnectionHealthChecked`, `StoreAppsDiscovered` — Sprint 2.8/2.9) narram o que aconteceu com a Store Connection como entidade de negócio, mas nenhum carrega duração, código de erro estável, ou marcação de retry — não dava para computar latência/success-rate/retry-rate a partir deles sem sobrecarregar seu propósito.
**Decisão:** Criado um evento novo, `StoreConnectionCallCompleted`, explicitamente classificado como "operacional" (não de domínio) — uma linha por chamada externa individual, existe só para alimentar métricas de observabilidade. Os eventos de domínio continuam existindo e sendo emitidos exatamente como antes, sem nenhuma alteração.
**Motivo:** Um evento de domínio responde "o que aconteceu com esta entidade de negócio" (relevante para quem lê a história da Store Connection); um evento operacional responde "como o sistema se comportou tecnicamente" (relevante para observabilidade). Fundir os dois deixaria o payload de domínio poluído com detalhes técnicos (duração, retry) que não fazem parte da história de negócio, ou o operacional incompleto por causa de restrições do domínio.
**Impacto:** Todo evento futuro precisa ser classificado explicitamente como domínio ou operacional antes de ser criado — nunca adicionar um campo técnico (duração, latência, retry) a um evento de domínio existente "porque já está ali"; criar um evento operacional novo se for esse o caso.

### [2026-08-09] `errorCode` estável (`classifyHttpStatus`) é um conceito novo, separado da mensagem sanitizada já existente
**Contexto:** As mensagens de erro sanitizadas (`sanitizeHttpError`/`sanitizeAppleError`/`sanitizeGoogleError`, Sprint 2.9/2.10) foram desenhadas para exibição ao usuário — texto em português, pode mudar de redação sem aviso. Para métricas (`errorCode` no evento operacional), era preciso algo estável que não quebrasse se o texto da mensagem mudasse, e que fosse comparável entre providers (a Apple pode responder `200` com um código de erro no corpo, não só via status HTTP).
**Decisão:** `classifyHttpStatus()` (`packages/integrations/src/core/errors.ts`) — um conjunto fixo e pequeno de buckets (`UNAUTHORIZED`/`FORBIDDEN`/`NOT_FOUND`/`RATE_LIMITED`/`SERVER_ERROR`/`UNEXPECTED_ERROR`/`UNKNOWN`), nunca o texto da mensagem nem o status HTTP cru. `HealthResult`/`ListResult`/`ItemResult` ganharam um campo `code?: string` opcional só para isso.
**Motivo:** Separar "o que o usuário vê" de "o que a métrica agrupa" evita que uma melhoria de copywriting (mudar o texto de uma mensagem de erro) quebre silenciosamente um gráfico de Failure Rate por código de erro.
**Impacto:** Todo adapter futuro (Steam, etc.) que retornar um erro deveria popular `code` com um dos buckets existentes (ou propor um novo, deliberadamente, não um valor livre por provider).

### [2026-08-09] Painel de Integration Health vive em `/settings/store-connections`, não em um widget de Dashboard
**Contexto:** O escopo do usuário permitia os dois locais ("Dashboard ou `/settings/store-connections`, escolhendo o local que melhor respeite a arquitetura existente").
**Decisão:** Painel embutido em cada card de Store Connection existente, não um widget novo no Dashboard.
**Motivo:** As métricas pedidas (status, success/failure rate, latência) são inerentemente por-conexão — Apple e Google têm comportamentos e credenciais completamente separados, então "Integration Health" sem contexto de qual conexão não responde a pergunta nenhuma sozinho. A tela de Store Connections já tem esse contexto renderizado por card; um widget de Dashboard precisaria decidir como resumir/agregar múltiplas conexões antes de fazer sentido, uma decisão de produto não pedida neste sprint.
**Impacto:** Se um resumo agregado (ex.: "3 de 4 integrações saudáveis") fizer sentido no Dashboard no futuro, é um sprint novo, não uma extensão trivial deste — decisão de agregação cross-conexão fica em aberto.

### [2026-08-09] CRÍTICO: `platforms` estava vazia em produção desde o Sprint 1.7/2.8 — ninguém nunca conseguiu criar uma Store Connection real
**Contexto:** Fase 0 do Sprint 2.11 (smoke-check de produção do painel Integration Health, Sprint 2.10.1) — o botão "Add Connection" apareceu desabilitado em produção com a conta de teste `teste@aigamestudioos.com`. Investigação (REST direto, autenticado) confirmou `GET /rest/v1/platforms` retornando `[]`.
**Causa raiz:** as linhas de `platforms` (`App Store`/`Google Play`/`Steam`) só existiam em `supabase/seed.sql`/`supabase/seed/01_global.sql`. O Supabase CLI nunca aplica `seed.sql` a um projeto hospedado/linkado — só a `supabase db reset` local. Nenhuma migration jamais fez `insert into platforms`, então a tabela ficou genuinamente vazia em produção desde a criação do schema (Sprint 1.7/2.8). ### [2026-08-10] CRÍTICO: hard-delete de Studio é incompatível com Event Store append-only + FK circular studios↔users — regressão real de produção causada pelo cleanup do GATE 9 (Sprint 2.11a), corrigida, e nova política de cleanup adotada
**Contexto:** Ao validar produção do Sprint 2.11b, `bootstrap_studio_for_current_user()` começou a falhar para QUALQUER conta nova (`23503` em `fk_studios_owner_user_id`). **Decisão:** Hard-delete de Studio é hoje **arquiteturalmente incompatível** com (a) Event Store append-only e (b) FK circular `studios↔users` sem uma transação única cobrindo ambos os lados. **Motivo:** Preferir uma política de cleanup que respeite as garantias de auditoria/integridade referencial já decididas (Event Store nunca perde histórico; nenhuma linha é apagada só para "arrumar" um teste) a forçar uma exclusão que exigiria desabilitar uma regra de imutabilidade ou reintroduzir a mesma classe de bug do achado acima.
**Impacto:** Studios/Users QA de sessões de validação em produção **não são mais "zero resíduo"** — são resíduo QA intencional e auditável (Studio + owner banido + eventos append-only), sempre identificável pelo nome/email com prefixo `qa-`. **Débito técnico registrado, não resolvido nesta sessão:** falta uma política oficial de lifecycle/deletion de Studio (soft-delete via `archived_at`, tombstone de principals, retenção/anonimização de Event Store, processo formal de dados de QA em produção) — necessária antes que qualquer sprint futuro precise remover um Studio de verdade (não só QA).

### [2026-08-12] Sprint 2.11c — Idempotência do retry: reiniciar do zero (novo BuildUpload), nunca retomar uploadOperations parciais
**Contexto:** Auditados os 5 casos de falha parcial pedidos: (A) falha antes de criar BuildUpload — nada a limpar, retry cria tudo do zero, seguro. (B) BuildUpload criado, reserva de arquivo falha — `apple_build_upload_id` já persistido na linha antes da reserva; retry precisa descartar esse BuildUpload órfão antes de criar um novo (feito no `finally`, `committed=false`). (C) alguns chunks enviados, um falha no meio — a documentação oficial da Apple não expõe nenhum mecanismo para retomar upload de uma `uploadOperation` específica após falha do cliente (as `uploadOperations` são emitidas uma vez, na reserva; não há endpoint para "re-emitir a partir do byte X"); a política adotada é reiniciar do zero. (D) todos os chunks enviados, commit falha — mesmo caso: sem confirmação de que a Apple aceita um segundo `PATCH uploaded:true` idempotente após um primeiro `PATCH` malsucedido (não documentado), a política de retry ainda descarta e recomeça. (E) commit terminou mas o polling (GET) falha/expira — **este caso é diferente dos outros 4**: a entrega já aconteceu (commit teve sucesso), então NUNCA descartamos o BuildUpload aqui; persistimos `status=UPLOADING`, `apple_upload_state` com o último valor conhecido, e paramos — sem fingir sucesso nem falha.
**Decisão:** Granularidade de retry = a tentativa inteira (criar BuildUpload → reservar → upload → commit → poll), igual ao padrão já usado no Google — nunca retry por chunk individual. Retry sempre cria um `BuildUpload` novo; nunca tenta reaproveitar `uploadOperations` de uma tentativa anterior.
**Motivo:** Sem documentação oficial confirmando semântica idempotente de retomada parcial nesta API, assumir que é seguro retomar seria um risco real (poderia duplicar o arquivo entregue, ou falhar de forma não sanitizada). Reiniciar do zero é mais lento mas comprovadamente seguro dentro do que a documentação garante.
**Impacto:** Débito técnico aceito — um retry após falha tardia (caso C/D) refaz o download do Storage e o upload completo à Apple, mesmo que a maior parte já tivesse sido transferida. Resolver isso de verdade exigiria rastrear estado de sessão de upload entre tentativas, o que é trabalho de fila/job (Sprint 2.11d), não deste sprint.

### [2026-08-14] Sprint 2.11d-2a — Continuação bounded nunca incrementa `attempt`; só `RETRY_WAIT`/`DEAD` incrementam
**Contexto:** `checkpoint_and_release_integration_job()` (continuação — o processor ainda tem trabalho a fazer, ex.: mais chunks) e `complete_integration_job()` com `p_status='RETRY_WAIT'` (falha classificada como retryable) parecem semanticamente próximos ("o job volta para um estado não-terminal"), mas são conceitualmente diferentes: continuação é a MESMA tentativa avançando; retry é uma NOVA tentativa depois de uma falha.

**Impacto:** Nenhum débito — decisão já implementada corretamente desde a primeira versão da migration, testada empiricamente (job de teste com 3 passos terminou com `attempt=1` inalterado ao longo de 3 invocations separadas do dispatcher).

Causa raiz: `middleware.ts` protege toda rota por padrão (allowlist `PUBLIC_ROUTES`), e a chamada não tem cookie de sessão (é feita por `pg_net`, nunca por um browser autenticado).

**Motivo:** Misturar os dois conceitos (rota pública vs. rota com autenticação alternativa) na mesma allowlist confundiria o próximo desenvolvedor a interpretar `PUBLIC_ROUTES` como "seguro adicionar aqui sempre que uma rota não precisar de sessão de usuário", quando na verdade só faz sentido para rotas genuinamente sem controle de acesso.
**Impacto:** Bug real, encontrado e corrigido durante a implementação deste sub-sprint (não teria sido descoberto sem o teste empírico contra um servidor real — um teste só da função `isValidDispatcherSecret()` isolada nunca veria o middleware). Registrado em `IMPLEMENTATION_LOG.md`.

### [2026-08-15] Sprint 2.11d-2c — Bug pré-existente: `service_role` nunca teve GRANT de tabela, só RLS
**Contexto:** Ao testar o worker Google de ponta a ponta pela primeira vez (`createAdminClient()` fazendo `.from("provider_uploads").select()` direto), a chamada falhou com `permission denied for table provider_uploads`. O mesmo bug, para o role `authenticated`, já tinha sido encontrado e corrigido no Sprint 1.7 (`20260717000003_grant_authenticated_privileges.sql`) — mas o equivalente para `service_role` nunca foi percebido, porque todo código anterior usando a service key passava por RPCs `SECURITY DEFINER` (que rodam como o dono da função, contornando o problema), nunca por acesso de tabela direto.
**Decisão:** `20260815000001_grant_service_role_privileges.sql` — mesmo padrão exato do Sprint 1.7, aplicado a `service_role`: `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO service_role` + `ALTER DEFAULT PRIVILEGES` (para tabelas futuras).
**Motivo:** Conceder isso não reduz segurança nem é um "presente" novo de privilégio — `service_role` já tem acesso irrestrito por design (é a chave administrativa do projeto, usada só em código server-only nunca exposto ao browser) e já bypassa RLS inteiramente; faltava só o `GRANT` de tabela que o Postgres exige como primeiro portão antes de RLS ser avaliado. Sem ele, qualquer código futuro que precisasse fazer acesso de tabela direto como `service_role` (não só via RPC) teria o mesmo erro.
**Impacto:** Bug real corrigido, encontrado só porque o worker é o primeiro código do projeto a fazer esse tipo de acesso — não foi detectado antes por falta de teste de acesso direto de tabela como `service_role`, não por um erro de implementação deste sprint. ### [2026-08-14] Readiness é uma RPC pura calculada on-demand — não uma view, não uma coluna materializada
**Contexto:** O Sprint 2.12a precisava responder "esta Release pode ser submetida?" combinando sete tabelas (`releases`, `submissions`, `builds`, `build_artifacts`, `store_connections`, `provider_uploads`, `games`/`game_localizations`). Três formas eram viáveis: uma view, uma RPC calculada a cada chamada, ou materializar o veredito (coluna `is_ready` na Release, ou tabela de resultados de check).
**Decisão:** RPC Postgres `get_release_readiness(release_id)` (`SECURITY DEFINER`), que recalcula tudo e devolve `{status, blockerCount, checks[]}` em jsonb. Nenhum estado de readiness é persistido em lugar nenhum.
**Motivo:** Materializar seria stale por construção — o veredito muda por caminhos que não passam pela Release (o worker de upload conclui um `provider_upload`, alguém troca a credencial da Store Connection, o Game ganha `package_name`), e manter isso correto exigiria triggers em seis tabelas, cada uma um ponto novo de bug. Uma view foi descartada por dois motivos concretos: o resultado é uma lista heterogênea de checks por Submission (não uma linha por entidade), e a autorização precisa FALHAR ALTO em cross-Studio, não apenas devolver zero linhas como faria uma view sob RLS. Sendo pura, a readiness é determinística e sobrevive a reload/login/outro dispositivo por construção — não existe nenhum estado de UI envolvido.
**Impacto:** Nenhum código pode cachear ou copiar o veredito de readiness (nem em coluna, nem em tabela, nem em estado de cliente persistido) — a RPC é a única fonte da verdade e deve ser rechamada quando o resultado importa. Se um dia o custo virar problema, a saída é caching explícito com invalidação declarada, nunca uma coluna denormalizada.

### [2026-08-14] Catálogo de checks de readiness é uma TABELA global semeada por migration, não uma constante TypeScript
**Contexto:** O GATE 3 do 2.12a pedia um catálogo formal de checks (code, description, severity, blocking, source_of_truth, platform_scope). Cabia em `packages/database` como constante tipada, ou no banco como tabela global.
**Decisão:** Tabela `readiness_check_definitions` (global, sem `studio_id`, RLS de leitura para `authenticated`), semeada por migration; o TypeScript recebe severity/blocking já embutidos em cada check devolvido pela RPC, em vez de manter uma cópia paralela.
**Motivo:** Quem avalia os checks é SQL (a RPC). Se o catálogo vivesse em TypeScript, o SQL teria códigos literais espalhados que nada obrigaria a bater com a constante — a divergência seria silenciosa. Com a tabela, a própria RPC lê severity/blocking do catálogo, então mudar a severidade de um check é uma linha de migration e vale imediatamente no gate. É também o padrão já usado no repo para `permissions` (Sprint 1.8d-4) e `platforms`.
**Impacto:** Adicionar um check novo é sempre duas partes na mesma migration: a linha no catálogo e a emissão na RPC. Um código emitido pela RPC sem linha no catálogo simplesmente some do resultado (o `readiness_check_entry` faz join) — falha visível em teste, por desenho.

### [2026-08-14] Requisito de loja não modelado devolve NOT_APPLICABLE, nunca PASS
**Contexto:** Screenshots, ícone de loja, classificação indicativa e política de privacidade são obrigatórios nas lojas reais, mas não existem no schema do AGSOS hoje (GATE 6). Omitir esses checks deixaria a readiness parecendo mais completa do que é.

**Motivo:** Um `PASS` fabricado é pior que a ausência do check: transformaria "o sistema não sabe" em "o sistema verificou e está tudo certo", exatamente o tipo de mentira que uma tela de readiness não pode contar antes de uma submissão à loja. `NOT_APPLICABLE` mantém o requisito à vista para o 2.12b sem bloquear um usuário que não tem como satisfazê-lo dentro do produto.
**Impacto:** Quando o schema desses assets existir, cada check migra de `NOT_YET_MODELED` para `IMPLEMENTED` na mesma migration que cria a tabela — e só então pode virar `BLOCKER`.

**Contexto:** Fecha o achado do Sprint 2.12c ("Duplicate Submission: nenhuma prevenção existe hoje"). **Validação:** `scripts/test-readiness-golden-path.mjs` (GATE 14, expandido) prova, via HTTP real (PostgREST): 2ª Submission sequencial idêntica rejeitada com unique violation; corrida real (`Promise.all` de duas criações concorrentes para o mesmo Release+Platform) resolve deterministicamente para exatamente 1 sucesso + 1 rejeição (mesma unique violation, não outro erro); resubmissão após a anterior virar `REJECTED` é aceita. `supabase/tests/readiness_test.sql` também precisou de fixture atualizado (ver GATE 2 abaixo) para continuar passando com o novo gate de permissão, mas a lógica do índice em si é testada só pelo script HTTP (que já exercita `submissions` via sessão autenticada real, ao contrário do teste SQL que é focado em `get_release_readiness`).

### [2026-08-17] Sprint 2.14 — Causa raiz de `SUBMISSION_TARGETS_MISSING` bloqueando a 1ª Submission: Submission Gate (UI), não o RPC nem uma entidade `SubmissionTarget`

**Contexto:** Débito herdado desde o Sprint 2.12b (ver entrada acima) e contornado por fixture no Sprint 2.13: um Release sem nenhuma Submission ativa sempre reprova o check `SUBMISSION_TARGETS_MISSING` (`BLOCKER`), e a página `/publishing` usava `readiness.status === "READY"` puro para habilitar "Criar Submissão" — então o botão nunca habilitava para a 1ª Submission de um Release, mesmo com tudo mais pronto.

**Investigação (Fase A, read-only):** Confirmado por `grep` em todo o repositório que **não existe** tabela, tipo ou repository `submission_targets`/`SubmissionTarget` — o termo só aparece como `code` do catálogo `readiness_check_definitions` (`20260814170230_readiness_check_definitions.sql`). "Submission Target" é a forma como o catálogo se refere a uma `Submission` na sua função de declarar "esta Release publica nesta plataforma" — a própria linha de `submissions` já é o Submission Target; não há ownership novo para redefinir. Lido `get_release_readiness` (`20260814170321_get_release_readiness.sql`): `SUBMISSION_TARGETS_MISSING` é `FAIL` sse `not exists (select 1 from submissions where release_id = ... and archived_at is null)` — condição de nível Release, avaliada uma única vez fora do loop por Submission. Todos os demais checks (`ARTIFACT_*`, `STORE_CONNECTION_*`, `PROVIDER_UPLOAD_*`, `BUILD_*`) só existem **dentro** desse loop — ou seja, para uma Release com zero Submissions, o único check possível é este, e ele é estruturalmente inevitável: não há como "readiness de uma Submission que ainda não existe" ser avaliada antes dela existir. Lido `submissions-repository.ts::create()` — um `insert` direto, sem nenhuma dependência de `get_release_readiness`; a criação da Submission em si nunca esteve gated pelo RPC no backend, só o botão da UI estava.

**Resposta às perguntas do prompt:** (A) SubmissionTarget = a própria Submission, na função de target de publicação. (B) Owner = Submission (não há entidade separada). (C) Identidade = `(release_id, platform_id)`, igual à Submission. (D) Deveria existir desde a criação da Submission — não antes; não é uma pré-condição, é o próprio evento. (E) Quem cria é quem cria a Submission (usuário, via UI, mesmo fluxo de sempre). (F) Um Release READY (`RELEASE_STATUS_NOT_SUBMITTABLE` PASS) chega ao fluxo de criação sem targets porque "ter targets" e "estar num status submetível" são propriedades independentes — a primeira só passa a ser verdadeira depois da ação que o usuário está prestes a fazer. (G) Era **validação correta disparada no momento errado** — o RPC está certo (uma Release sem Submission genuinamente não tem plataforma-alvo), o defeito era o Submission Gate (UI) tratar esse veredito como um blocker de uma ação que ela mesma existe para resolver. (H) As fronteiras Readiness/Provider Upload/Submission/Store Review/Publication (`DEFINITION_OF_DONE.md` §12) permanecem intactas — nenhuma foi cruzada. (I) A correção não exige nenhuma mudança de Universal Language.

**Stop Condition avaliada e descartada:** nenhuma das condições de parada (§5 do prompt) se aplica — não foi necessário redefinir ownership (não existe outro para redefinir), não foi necessário alterar lifecycle de Release, não foi criada nova etapa de produto, nenhum contrato existente foi quebrado, nenhuma migration foi necessária. A correção é inteiramente client-side.

**Decisão:** O RPC `get_release_readiness` **não foi tocado** (mesma disciplina do 2.12c: não reabrir sem defeito real — e o defeito real não estava ali). Corrigido o Submission Gate: `apps/web/lib/readiness-status.ts` ganhou `isSubmissionGateBlocking(check)` (= `check.blocking && check.code !== "SUBMISSION_TARGETS_MISSING"`) e `isReadyForSubmissionGate(readiness)`, usados por `apps/web/app/publishing/page.tsx` (habilita "Criar Submissão") e por `apps/web/components/publishing/readiness-panel.tsx` (badge "Pronto para submissão"/"Não pronto" e o ícone/badge de cada `CheckRow`, para o painel nunca discordar do botão). O `check.blocking` cru devolvido pelo RPC continua sendo exibido como informação (o check aparece na lista, com uma badge neutra "Resolvido ao criar a Submission" em vez de "Bloqueia submissão") — a UI não esconde o veredito do RPC, só reinterpreta uma condição estruturalmente inevitável como não-acionável para o gate específico de criação.

**Por que isso não enfraquece nada:** a exclusão é de um único `code` (`SUBMISSION_TARGETS_MISSING`), que só é `FAIL` quando a Release tem zero Submissions ativas — no momento em que existe qualquer Submission (mesmo de outra plataforma), o check volta a `PASS` (a condição `not exists` deixa de valer) e nunca mais aparece. Todos os outros blockers (`STORE_CONNECTION_MISSING`, `ARTIFACT_*`, `PROVIDER_UPLOAD_*`, etc.) continuam avaliados e bloqueando normalmente assim que há uma Submission para avaliar — a 2ª+ Submission de um Release continua exigindo Release genuinamente READY, sem nenhuma mudança de comportamento.

**Validação:** `apps/web/e2e/critical-path.spec.ts` reescrito (GATE 1/4) — `apps/web/e2e/fixtures/seed.mjs` não pré-cria mais nenhuma Submission; o teste cria a 1ª Submission (Google Play) inteiramente pela UI a partir de zero Submissions, confirma persistência com reload de página, reabre o diálogo para a 2ª Submission (App Store) e reproduz o fluxo NOT_READY→corrige blocker→READY do 2.13 (agora avaliando os checks da 1ª Submission real, não mais de uma seed). `apps/web/app/publishing/page.test.tsx` ganhou um teste novo (`FIRST_SUBMISSION`) que reproduz o veredito exato do RPC para zero Submissions (só `SUBMISSION_TARGETS_MISSING`) e confirma que o botão habilita e `createSubmission` é chamado com os argumentos corretos.

### [2026-08-17] Sprint 2.16a — Submission Lifecycle Foundation: novos estados, RPC única, permissão `publishing.submit`, PRODUCTION GUARD

**GATE 0 (auditoria).** Confirmado por leitura direta do schema (não por memória de sprints anteriores): `submissions.status` (`submission_status`) nasce sempre `DRAFT` via `insert` direto em `submissions-repository.ts::create()` — nenhum RPC/trigger/Server Action jamais mudava esse valor. `WAITING` nunca é escrito por nenhum código real (DEFINED_BUT_UNREACHABLE); `APPROVED`/`PUBLISHED` também — não existe hoje nenhum mecanismo que os produza (Store Review ingestion nunca foi implementado). `store_reviews` foi lida e descartada como base para o mecanismo de execução: ela registra a *decisão* de um review já ocorrido (`decision`, `reviewer_notes`, `reviewed_at`), semanticamente distinta de "estou no meio de tentar enviar" — reusá-la teria misturado dois conceitos (Universal Language do §5/§19 da spec do sprint).

**Decisão de state machine:** `DRAFT → READY_TO_SUBMIT → SUBMITTING → SUBMITTED | FAILED`, `FAILED → READY_TO_SUBMIT` (retry). Três valores de enum novos (`READY_TO_SUBMIT`, `SUBMITTING`, `FAILED`), adicionados via `ALTER TYPE ... ADD VALUE` em migration própria (`20260817000001`) — Postgres não permite usar um valor de enum na mesma transação em que foi criado, por isso a lógica que os referencia ficou numa segunda migration (`20260817000002`), nunca no mesmo arquivo.

**Decisão de permissão:** `publishing.submit`, distinta de `publishing.create_submission`. Pergunta de domínio respondida (§8 da spec): "quem pode CRIAR uma Submission necessariamente pode ENVIÁ-LA à loja?" — não. Criar é registrar uma intenção local; enviar dispara transporte real e (eventualmente, com o guard ligado) consome quota de review de loja — maior risco/irreversibilidade, permissão própria. Owner/Admin ganham `publishing.submit` no backfill e no `bootstrap_studio_for_current_user`; Member continua só com `publishing.read`.

**Decisão de infraestrutura de job:** reaproveitado `integration_jobs`/dispatcher (Sprint 2.11d) — `provider_upload_id` virou nullable, `submission_id` foi adicionado, com `check` garantindo exatamente um dos dois preenchido. Nenhuma tabela `submission_jobs` paralela foi criada. O dispatcher genérico (`claim_integration_jobs`/`complete_integration_job`/checkpoint/lease) não precisou de nenhuma mudança — só os processors (`submission_google_play`/`submission_apple`, `apps/web/lib/jobs/processors/`) e o registro em `registry.ts` são novos.

**Decisão de idempotência:** `transition_submission` usa `select ... for update` (lock de linha) para serializar chamadas concorrentes na mesma Submission, e trata "ação já satisfeita" (ex.: `SUBMIT` chamado enquanto já `SUBMITTING`) como no-op (`noop: true`), nunca erro — cobre duplo clique/retry de rede sem nunca criar um segundo `integration_jobs` para a mesma Submission (também reforçado por uma checagem explícita de job ativo, mesmo padrão de `enqueue_provider_upload_job`, Sprint 2.11d).

**PRODUCTION GUARD (GATE 25 da spec do sprint).** Nenhuma chamada real que comite um Google Play Edit ou crie uma Apple Review Submission acontece neste sprint. `env.allowStoreMutation` (`AGSOS_ALLOW_STORE_MUTATION`, `apps/web/lib/env.ts`) tem que ser `"true"` para o processor sequer tentar — e nenhuma variável de ambiente/deploy até agora a define.
